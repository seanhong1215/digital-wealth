## 我們的理解

這不是一個要上線營運的產品，是**一份會被 30 秒掃過的技術履歷**，只是它剛好長得像一個 App。

真正的讀者是那位在桌機前開 repo 的技術主管。而 25–45 歲手機使用者是「劇本裡的角色」—— 為他們做的 mobile-first 決策，本身就是要給技術主管看的判斷力證據。

這個認知決定了兩件事的優先序：

1. **README 與專案結構是主視覺**，不是附屬品
2. **錯誤狀態是主打商品**，不是邊角案例 —— happy path 面試官三秒滑過，error handling 才會讓他停下來提問

### 本版的四項變更

| 項目 | 原本 | 現在 |
|---|---|---|
| 後端 | MSW mock | **真實後端**（NestJS + PostgreSQL + Redis） |
| 定位 | 前端作品集 | **全端作品集** |
| 部署 | Vercel 靜態部署 | **僅本機 Docker Compose** |
| 節奏 | 5 週封版 | **MVP 優先，逐單元確認理解** |

## 建議方案

### 一、總覽與持倉合併為單頁 ✅ 已採納

使用者情境是「通勤或睡前快速查看部位」。這種情境下打開 App 想看的就兩件事：**總共有多少錢、哪一檔在賺賠**。分成兩個分頁等於強迫使用者多點一次。

三個好處：產品判斷正確（面試時可主動說明取捨）、少一組載入狀態與測試、底部 Tab 從 4 個減為 3 個。

### 二、多步驟下單：step 走路由，表單資料不持久化 ✅ 已定案

重整後回到步驟 1，這是刻意的。**下單草稿本來就不該被還原** —— 使用者重整後看到一張已填好 500 股的確認頁，卻不記得是自己填的還是上次殘留，這是真實系統會出事的地方。

詳見 `05-specs/trade.md`。

### 三、Demo 控制台的故障注入移到後端 ✅ 已採納

原設計是 MSW handler 讀 Zustand store。改真後端後，故障注入放在**後端 middleware** —— 更真實，且證明前端對故障來源完全無感知。這是分層正確性的證明。

### 四、Demo 參數以 `_demo_` 前綴隔離 ✅ 已採納

明細篩選與 Demo 控制台都要寫 URL，不隔離會在同一個 query string 上打架。現在講是一句約定，等做到 Phase 4 才發現就是重構。

| 衝突 | UI 慣例 | 台股語意 | 解法 |

不處理的話，下單成功彈出的綠色勾勾在使用者的金融直覺裡是「跌」。詳見 `04-design-system.md`。

## 功能範圍

### MVP（不可再砍）

| 模組 | 前端 | 後端 |
|---|---|---|
| 資產總覽 ＋ 持倉（合併單頁） | 卡片、走勢曲線、持倉列表 | 聚合查詢、快照表 |
| 即時報價 | WS 訂閱、選擇性重繪、新鮮度降級 | WS Gateway、Redis 訂閱、扇出 |
| 下單流程 | 多步驟表單、樂觀更新、失敗回滾 | **DB transaction、行鎖、冪等鍵** |
| 交易明細 | 虛擬滾動、篩選、URL 同步 | cursor 分頁、複合索引 |
| 錯誤狀態 | error boundary、重試、降級 | 統一錯誤碼、Exception Filter |
| 最小認證 | 登入頁 | JWT ＋ httpOnly Cookie ＋ Guard |
| Demo 控制台 | 側邊抽屜 | 故障注入 middleware |

**交付物**：README（首屏＝架構決策）、60 秒 demo 影片、關鍵畫面截圖、`docker compose up` 一行啟動

### 可砍清單（由上往下砍）

1. **配置圓餅圖** —— 走勢曲線已展示圖表能力，屬重複訊號
2. **`heavy-history` 8,000 筆情境** —— 3,000 筆已足夠證明虛擬滾動
3. **Playwright 冒煙測試** —— 改為 README 手動檢查清單
4. **Demo 控制台故障種類由 5 種減為 3 種**

### 明確不做（README 需寫明理由）

註冊流程、OAuth、多使用者、線上部署、i18n、深色模式（token 分層已預留）、微服務拆分、K8s、K 線圖與技術指標、PWA。

## 設計方向

| 項目 | 決定 |
|---|---|
| 風格 | 高資料密度 ＋ 留白充足（Robinhood 的數字處理 × 富果的排版密度） |
| 主色 | 中性深藍 `#16243A`，11 階色階 |
| 強調色 | **靛藍系** `#6E6DE4`（脫離漲跌色的暖色區間） |
| 漲跌色 | 語意 token `up`/`down`/`flat` ＋ `▲▼` ＋ 正負號 |
| 字體 | Noto Sans TC；數字一律 `tabular-nums` |
| 可讀性下限 | 內文 16px；金額字重 ≥ 500 |
| 動效 | 只做狀態轉場（骨架屏、報價跳動閃爍 150ms），不做裝飾動畫 |

**明確避開**：傳統券商舊版下單頁（資訊密度爆炸、桌機思維硬塞手機）、動畫過重的 fintech 行銷頁（本專案是產品內頁，不是 landing page）。

## 網站結構（Sitemap）

```
App Shell（手機：底部 Tab Bar 3 項｜桌機 ≥1024px：左側導覽）
│
├── /login                         登入（單一 demo 帳號）
│
├── /  →  轉向 /portfolio
│
├── /portfolio                     資產  ★ 預設首頁
│   ├─ 智慧摘要                    一句話說出重點
│   ├─ 總覽卡片                    總資產、今日損益、現金、持股市值
│   ├─ 資產走勢曲線                近 30 日
│   └─ 持倉列表                    即時報價、漲跌、未實現損益
│      └─ 列展開                   成本、市值、報酬率（不另開路由）
│
├── /transactions                  明細
│   ├─ 篩選列                      類型、日期區間 → 同步至 URL
│   └─ 虛擬滾動列表                3,000+ 筆，日期分組
│
├── /trade                         下單
│   ├── /trade                     步驟 1：選擇標的
│   ├── /trade/:symbol             步驟 2：填寫委託 ＋ 費用試算
│   ├── /trade/:symbol/confirm     步驟 3：確認（二次確認）
│   └── /trade/:symbol/result      步驟 4：成功 / 被拒 / 逾時
│
├── /404                           找不到頁面
│
└── ⚙ Demo 控制台                  全域側邊抽屜，非路由
                                    狀態同步至 ?_demo_* 參數
```

**幾個刻意的決定：**

- **持倉不另開詳情頁** —— 展開列就夠，省一個路由與一組載入狀態
- **`/trade` 獨立於持倉** —— 下單是完整流程，不是持倉的子動作
- **結果頁是獨立路由** —— 下單被拒的畫面要能直接用連結分享
- **Demo 控制台不是路由** —— 它是覆蓋在任何頁面上的工具，做成路由會讓人離開正在看的畫面

## 時程預估

**分 5 階段、31 個單元。** 每個單元做完即停、導讀、確認理解才前進。

| 階段 | 內容 | 單元數 |
|---|---|---|
| Phase 0 | 地基：Docker Compose、schema、seed、金額型別 | 6 |
| Phase 1 | 讀取路徑：查詢 API、總覽頁、虛擬滾動 | 10 |
| Phase 2 | 即時路徑：market-feed、Redis pub/sub、WebSocket | 5 |
| Phase 3 | **寫入路徑：下單、交易一致性、樂觀更新回滾** | 6 |
| Phase 4 | 韌性與交付：錯誤契約、Demo 控制台、README | 4 |

**以全職 35–40 小時／週估算，含導讀與問答時間約 12–16 週。**

導讀與問答本身就是學習時間，不是額外開銷 —— 那是本專案的主要目的之一。

### 影響時程的關鍵因素

| 因素 | 影響 |
|---|---|
| Phase 3 的交易一致性 | 最高風險。DB 行鎖 ＋ 樂觀更新回滾第一次寫容易卡住 |
| Phase 2 的 WebSocket 重連 | 心跳、退避、狀態機的邊界情況多 |
| 學習節奏 | 若某個概念想深入研究，可以停在該單元多花時間 |
