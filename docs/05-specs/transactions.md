# 05-2 — 交易明細頁實作規格

> 情境 G 產出｜路由 `/transactions`｜對應單元 1.8–1.10
> 版本 0.1｜2026-08-13

---

## 頁面概述

顯示帳戶的完整帳務流水，**3,000 筆起跳**（`heavy-history` 情境 8,000 筆）。

這一頁要證明兩件事：**虛擬滾動的效能處理**、**URL 狀態同步的架構思考**。

### 版面結構

```
┌─────────────────────────────────┐
│ 頂部列：交易明細                  │
├─────────────────────────────────┤
│ 篩選列：[全部▾] [日期區間▾]  ✕清除│  ← 黏性（sticky）
├─────────────────────────────────┤
│ ── 今天 ──────────────  (黏性)   │
│  買進  台積電      -NT$ 1,086,546│
│         1 張 @ 1,085.00   09:23  │
│  手續費 台積電          -NT$ 1,546│
│ ── 昨天 ──────────────  (黏性)   │
│  賣出  聯發科      +NT$ 456,000  │
│  ⋯（虛擬滾動）                    │
├─────────────────────────────────┤
│ 底部 Tab Bar                     │
└─────────────────────────────────┘
```

## 元件規格

### `TransactionRow`

| 位置 | 內容 | 樣式 |
|---|---|---|
| 左上 | 類型中文（`買進`／`手續費`／`股利`⋯） | `--text-base` ／ `--weight-medium` |
| 左下 | 標的名稱 ＋ 數量 ＋ 單價（非交易類則顯示說明文字） | `--text-sm` ／ `--color-text-secondary` |
| 右上 | 金額（含正負號） | `--text-base` ／ `--weight-medium` ／ `tabular-nums` |
| 右下 | 相對時間 | `--text-sm` ／ `--color-text-secondary` |

| 項目 | 規格 |
|---|---|
| 列高 | **固定 76px** ← 見下方說明 |
| 分隔 | `border-bottom: 1px solid var(--color-border)` |
| 金額顏色 | 正數 `--color-text-primary`；負數 `--color-text-primary`。**不用漲跌色** |

> **買賣不使用漲跌色。** 漲跌色專屬於價格變動。「買進」不是「跌」，「賣出」不是「漲」。混用會讓使用者誤讀，這是 `03-presentation.md` 的硬性規則。
>
> 唯一例外：`DIVIDEND`（股利）可用 `--color-success`（靛藍），因為那是明確的正面事件。

> **列高必須固定。** 虛擬滾動需要預先知道每列高度才能計算捲動位置。動態高度雖然 TanStack Virtual 支援（`measureElement`），但會造成捲動時的高度重算與跳動。固定高度是效能與穩定性的取捨，值得在 README 說明。

### `DateGroupHeader`

| 項目 | 規格 |
|---|---|
| 文字 | `今天`／`昨天`／`8月10日`（相對時間規則見 `03-presentation.md`） |
| 樣式 | `--text-sm` ／ `--weight-semibold` ／ `--color-text-secondary` |
| 背景 | `--color-bg-page`（黏住時要遮住下方內容） |
| 高度 | 固定 36px |
| 定位 | `position: sticky; top: <篩選列高度>` |

> **黏性標題在虛擬滾動裡是個陷阱。** 被虛擬化的元素會被移出 DOM，`position: sticky` 就失效了。解法是**把日期標題也當成一種「列」放進虛擬清單**（`type: 'header' | 'row'`），或者用單獨的浮動標題層追蹤當前捲動位置。建議前者，實作簡單。

### `FilterBar`

| 項目 | 規格 |
|---|---|
| 定位 | `position: sticky; top: 0`，`z-index` 高於列表 |
| 背景 | `--color-bg-surface` ＋ `border-bottom` |
| 高度 | 56px |
| 內容 | 類型下拉（多選）｜日期區間｜清除按鈕（有篩選時才出現） |
| 已篩選提示 | 顯示筆數「符合 128 筆」 |

## URL 狀態同步 ★

**這一頁的核心架構訊號。**

### 業務參數（同步到 URL）

| 參數 | 範例 | 說明 |
|---|---|---|
| `type` | `?type=BUY,SELL` | 類型篩選，逗號分隔 |
| `from` | `?from=2026-07-01` | 起始日期 |
| `to` | `?to=2026-08-13` | 結束日期 |

**為什麼要同步到 URL：可分享性。** 使用者（或面試官）可以把「7 月的所有買進」這個畫面連結直接傳給別人。

### Demo 參數（前綴隔離）

| 參數 | 範例 |
|---|---|
| `_demo_scenario` | `?_demo_scenario=heavy-history` |
| `_demo_faults` | `?_demo_faults=api-500` |

> **`_demo_` 前綴是刻意的命名空間劃分。** Demo 控制台與明細篩選都要寫 URL，不隔離的話兩邊會在同一個 query string 上打架。Demo store 只讀寫 `_demo_` 開頭的 key，兩邊互不干擾。
>
> 這件事現在是一行約定，等做到 Phase 4 才發現就是重構。

### 不同步的狀態

| 狀態 | 為什麼不放 URL |
|---|---|
| 捲動位置 | 使用者不會想分享「捲到第 47 筆」 |
| 展開的列 | 純 UI 狀態 |
| cursor | cursor 是實作細節，且會讓網址變得很醜 |

## 互動狀態說明

| 狀態 | 觸發條件 | 視覺表現 |
|---|---|---|
| `default` | 資料載入完成 | 正常列表 |
| `loading`（首次） | 初次進頁 | 8 列 `Skeleton` 骨架，含日期標題骨架 |
| `loading`（載入更多） | 捲到接近底部 | 底部顯示 3 列骨架，**上方內容不動** |
| `empty`（無資料） | 帳戶無交易（`new-user`） | `EmptyState`「尚無交易紀錄」＋「開始下單」按鈕 |
| `empty`（篩選無結果） | 篩選後 0 筆 | `EmptyState`「沒有符合條件的紀錄」＋**「清除篩選」按鈕** |
| `error` | API 失敗 | 頁面級 `ErrorState` ＋ 重試 |
| `error`（載入更多失敗） | 分頁請求失敗 | **底部顯示重試列**，已載入的內容保留 |
| `offline` | WebSocket 斷線 | **本頁不受影響** —— 明細是歷史資料，不依賴即時報價 |

> **兩種 `empty` 必須分開處理。** 「你還沒有交易」和「這個篩選條件沒結果」是完全不同的訊息，行動按鈕也不同（前者「去下單」、後者「清除篩選」）。這是很常見的偷懶點。

> **`offline` 狀態下本頁完全正常。** 這正是降級設計的展示點 —— 報價斷了，歷史資料仍然可用。

## 響應式斷點規則

| 斷點 | 版型 |
|---|---|
| < 640px | 單欄，資訊上下兩行（左側類型/標的、右側金額/時間） |
| ≥ 768px | 改為表格式：類型｜標的｜數量｜單價｜金額｜結餘｜時間 各自成欄 |
| ≥ 1024px | 左側導覽；表格寬度上限 1200px 置中；顯示 `balance_after_cents`（結餘）欄 |

> **結餘欄只在桌機顯示。** 手機空間不足，且散戶較少用到；但桌機顯示它能展示帳務設計的完整度。

## 效能要求

| 項目 | 目標 | 量測方式 |
|---|---|---|
| 捲動流暢度 | **3,000 筆捲動 5 秒內無 long task > 50ms** | Chrome DevTools Performance，**CPU 4x throttling** |
| DOM 節點數 | 任何時刻 ≤ 30 列在 DOM 中 | Elements 面板檢查 |
| 首屏 | 骨架 200ms 內出現 | — |

> **判準必須帶量測條件。** 「捲動維持 60fps」沒有裝置與節流設定就不是判準，只是願望。

### 虛擬滾動設定

| 參數 | 值 | 理由 |
|---|---|---|
| `estimateSize` | 76（列）／36（日期標題） | 固定高度，不需 `measureElement` |
| `overscan` | 5 | 上下各多渲染 5 列，減少快速捲動時的空白 |
| 觸發載入更多 | 距底部 300px | 提前載入，使用者感覺不到分頁 |

## Handoff 注意事項

### 容易踩的坑

1. **cursor 是不透明字串** —— 後端回傳的 `nextCursor` 是 base64 編碼，前端**不要解析它**，原樣傳回去即可。解析它等於依賴後端的排序實作。

2. **黏性日期標題要放進虛擬清單** —— 被虛擬化的元素會離開 DOM，`sticky` 會失效。把標題當成一種列型別處理。

3. **切換篩選時要重置 cursor** —— 否則會拿舊 cursor 去查新條件，結果錯亂。TanStack Query 的 query key 要包含所有篩選參數，讓它自動視為不同查詢。

4. **列高固定 76px 不可變** —— 動態高度會讓捲動位置計算失準。長標的名稱用省略號，不換行。

5. **`_demo_` 前綴不可省略** —— Demo 參數與業務參數必須隔離。

6. **載入更多失敗時不要清空列表** —— 已載入的資料要保留，只在底部顯示重試。

### 與設計的已知差異

- 無 Figma 設計稿，以 `04-design-system.md` 的 token 為準
- 日期區間選擇器暫用原生 `<input type="date">`，不客製日曆元件（成本高、非本專案重點）
