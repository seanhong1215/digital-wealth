# 05-3 — 下單流程實作規格

> 情境 G 產出｜路由 `/trade/*`｜對應單元 3.4–3.6
> 版本 0.1｜2026-08-13

> **本專案技術含量最高的頁面。** 多步驟表單、樂觀更新、失敗回滾、冪等處理都在這裡。

---

## 流程概述

四個步驟，每一步是獨立路由。

```
/trade                      步驟 1：選擇標的
   │                        搜尋框 ＋ 從持倉快選
   ▼
/trade/:symbol              步驟 2：填寫委託
   │                        買/賣、數量、限價 ＋ 即時試算
   ▼
/trade/:symbol/confirm      步驟 3：確認
   │                        大字級金額 ＋ 費用明細 ＋ 二次確認
   ▼
/trade/:symbol/result       步驟 4：結果
                            成功 / 被拒 / 逾時 三種分支
```

## URL 策略定案 ★

**這是 `01-proposal.md` 留下的待決事項，本文件定案。**

| 項目 | 決定 | 理由 |
|---|---|---|
| **步驟（step）** | **走路由** | 瀏覽器上一頁能回到前一步；每一步可被書籤與分享 |
| **表單資料** | **只存記憶體，重整就回到步驟 1** | 見下方說明 |
| **`idempotencyKey`** | 進入步驟 3 時產生，存記憶體 | 見下方說明 |
| **結果頁** | 獨立路由，帶 `orderId` query | 下單被拒的畫面要能直接分享給面試官看 |

### 為什麼表單資料不持久化

**金融場域的正確答案：下單草稿本來就不該被還原。**

想像使用者重整後看到一張已經填好「買進 500 股」的確認頁，卻不記得是自己剛填的還是上次殘留的。這是真實系統會出事的地方。

**對照組**：交易明細的篩選條件**要**同步到 URL。兩者的差別是：

| | 明細篩選 | 下單表單 |
|---|---|---|
| 分享價值 | 高（「你看 7 月的買進」） | 無（沒人要分享未送出的委託） |
| 意圖新鮮度 | 不重要 | **關鍵** —— 舊的下單意圖是危險的 |
| 誤操作後果 | 看到不對的列表 | **送出不想要的委託** |

> 「為什麼明細篩選要同步 URL，但下單表單不要？」是很好的面試素材。答案是「可分享性」與「意圖新鮮度」的取捨，這比會寫 `useSearchParams` 值錢得多。

### 為什麼 `idempotencyKey` 在步驟 3 產生

**不是在按下送出時產生。**

如果在送出時才產生，使用者連點兩次會產生兩把不同的 key，冪等就完全失效了。

正確做法：**進入確認頁時產生一次**，存在該步驟的狀態裡。連點多少次送出，帶的都是同一把 key，後端能正確識別為重複請求。

```tsx
// 進入確認頁時產生，用 useState 的 lazy initializer 確保只執行一次
const [idempotencyKey] = useState(() => crypto.randomUUID());
```

## 各步驟規格

### 步驟 1 — 選擇標的（`/trade`）

| 區塊 | 內容 |
|---|---|
| 搜尋框 | 輸入代號或名稱，**debounce 300ms** 後查詢 `GET /instruments?q=` |
| 我的持倉 | 快選列表，直接列出持倉標的（賣出情境的主要入口） |
| 搜尋結果 | 代號 ＋ 名稱 ＋ 現價 ＋ 漲跌 |

**狀態**：`default` / `loading`（搜尋中） / `empty`（查無結果） / `error`

### 步驟 2 — 填寫委託（`/trade/:symbol`）

| 欄位 | 規格 | 驗證 |
|---|---|---|
| 標的資訊 | 名稱、現價、漲跌（即時更新） | — |
| 買／賣 | 分段控制（Segmented Control），預設「買進」 | 必填 |
| 數量 | `NumberInput`，單位「股」，快捷鈕：1 張／5 張／全部 | 整數、> 0；賣出時 ≤ 持股數 |
| 限價 | `NumberInput`，預設帶入現價 | > 0；須符合 tick size；不得超出漲跌停 |
| 試算區 | `OrderPreview`：股款、手續費、證交稅、**總計** | 由 `POST /orders/preview` 取得 |

**驗證時機**：

| 時機 | 做什麼 |
|---|---|
| 輸入時 | 格式驗證（zod schema，`shared/`） |
| 失焦時 | 業務驗證（持股是否足夠、價格是否超出漲跌停） |
| 試算 | 數量或價格變動後 **debounce 500ms** 呼叫 `/orders/preview` |

> **費用一律由後端試算。** 費率規則（0.1425%、最低 20 元、賣出加 0.3% 稅）是業務規則，前後端各算一次就會兜不攏。

> **tick size 驗證要在前端做一次。** 台股跳動單位是分級的（股價 <10 跳 0.01、10–50 跳 0.05⋯），規則實作在 `shared/`，前端即時提示、後端最終把關。

### 步驟 3 — 確認（`/trade/:symbol/confirm`）

**這一頁的設計目標是「讓使用者慢下來」。**

| 項目 | 規格 |
|---|---|
| 標題 | `請確認委託內容` |
| 買賣方向 | **大字級 ＋ 明確文字**（`買進` / `賣出`），不只用顏色 |
| 標的 | 名稱 ＋ 代號，`--text-xl` |
| 數量與價格 | `1 張（1,000 股）@ NT$ 1,085.00`，`--text-lg` |
| 費用明細 | 股款、手續費、證交稅**分項列出** |
| **總計** | `--text-3xl` ／ `--weight-bold` ／ 醒目框線 |
| 提示 | 「送出後無法取消」 |
| 送出按鈕 | `Button variant="primary" size="lg"`，全寬，高度 ≥ 52px |
| 返回 | 次要按鈕「返回修改」 |

> **二次確認是為 55+ 使用者做的，但所有人都受益。** `PROJECT.md` §3 的要求：關鍵操作二次確認。

> **買賣方向不能只靠顏色區分。** 買進與賣出的後果完全相反，必須用文字明確標示。

### 步驟 4 — 結果（`/trade/:symbol/result?orderId=...`）

三種分支：

| 分支 | 觸發 | 顯示 |
|---|---|---|
| **成功** | `status: FILLED` | 靛藍勾勾（**不用綠色**）／成交明細／「查看明細」＋「再下一單」 |
| **被拒** | `ORDER_REJECTED` 等 4xx | 玫瑰紅叉／**明確的拒絕原因**／「返回修改」按鈕 |
| **逾時** | 請求逾時 | 橘色警示／「委託狀態未知，請至明細確認」／「查看明細」按鈕 |

> **成功用靛藍不用綠色。** 台股綠 = 跌 = 壞消息，綠色勾勾在使用者的金融直覺裡是矛盾的。見 `04-design-system.md`。

> **逾時分支必須做。** 這是最真實也最容易被忽略的情境 —— 請求送出了但沒收到回應，**委託可能成立也可能沒有**。這時絕對不能說「下單失敗」（可能已經成交了），只能說「狀態未知，請確認」。這個細節會讓面試官眼睛一亮。

## 樂觀更新與回滾 ★

### 流程

```
使用者按下送出
      │
      ▼
onMutate：立刻更新本地快取
      ├─ accounts 快取：現金扣掉總計
      ├─ positions 快取：股數增加
      └─ 保存「異動前的快照」← 回滾用
      │
      ▼
畫面立刻反映（使用者感覺是瞬間的）
      │
      ├─── 成功 ──► onSuccess：用伺服器回傳的權威值覆蓋快取
      │
      └─── 失敗 ──► onError：用快照還原快取
                            │
                            ▼
                     導向結果頁「被拒」分支
```

### 實作要點

```tsx
useMutation({
  mutationFn: submitOrder,

  onMutate: async (order) => {
    // 1. 取消進行中的查詢，避免它們覆蓋我們的樂觀更新
    await queryClient.cancelQueries({ queryKey: ['account'] });

    // 2. 保存快照 —— 這是回滾的依據
    const snapshot = {
      account: queryClient.getQueryData(['account']),
      positions: queryClient.getQueryData(['positions']),
    };

    // 3. 樂觀更新
    queryClient.setQueryData(['account'], optimisticAccount);

    return snapshot;  // 傳給 onError
  },

  onError: (err, order, snapshot) => {
    // 用快照還原
    queryClient.setQueryData(['account'], snapshot.account);
    queryClient.setQueryData(['positions'], snapshot.positions);
  },

  onSettled: () => {
    // 無論成敗，最後都跟伺服器對齊一次
    queryClient.invalidateQueries({ queryKey: ['account'] });
  },
});
```

### 三個容易出錯的地方

1. **`onMutate` 必須先 `cancelQueries`** —— 否則一個進行中的 `GET /accounts/me` 回來後會用舊資料覆蓋掉你的樂觀更新。

2. **回滾期間又收到 WebSocket 報價更新** —— 報價更新的是 `quotes` 快取，與 `account`／`positions` 是**不同的 query key**，兩者不會互相干擾。這是 query key 設計正確的好處。

3. **`DUPLICATE_REQUEST`（409）不算失敗** —— 使用者連點兩次，第二次回 409。這時**不該回滾也不該顯示錯誤** —— 第一次已經成功了。前端要把 409 當成成功處理，顯示原本的結果。

> 「技術上的錯誤」不等於「該讓使用者看到的錯誤」。這條值得寫進 README。

## 互動狀態說明

| 狀態 | 觸發條件 | 視覺表現 |
|---|---|---|
| `default` | — | 正常表單 |
| `loading`（試算） | 數量／價格變動後 | 試算區顯示 `Skeleton`，**送出鈕停用** |
| `loading`（送出中） | 按下送出 | 按鈕進入 `loading`，**停用並防止重複點擊**；全頁遮罩防止操作 |
| `empty` | 步驟 1 查無標的 | `EmptyState`「找不到符合的標的」 |
| `error`（驗證） | 欄位格式或業務規則不符 | 欄位下方紅字 ＋ 送出鈕停用 |
| `error`（餘額不足） | `INSUFFICIENT_FUNDS` | 紅色提示 ＋ **顯示差額**「尚缺 NT$ 12,000」 |
| `error`（下單被拒） | `ORDER_REJECTED` | 導向結果頁被拒分支 ＋ 樂觀更新回滾 |
| `offline` | WebSocket 斷線 | 橘色橫幅「報價中斷」；**現價欄位標示為舊資料**；仍可下單（限價單不依賴即時報價） |

> **報價中斷時仍可下單。** 這是限價單的特性 —— 使用者自己指定價格，不需要即時報價。但要明確標示現價是舊的，讓使用者知道參考值可能過時。

## Handoff 注意事項

### 容易踩的坑

1. **`idempotencyKey` 在進入確認頁時產生，不是按下送出時** —— 否則連點會產生不同 key，冪等失效。

2. **重整會回到步驟 1，這是刻意的** —— 不要為了「體驗更好」把表單資料存進 sessionStorage。

3. **409 要當成功處理** —— 不回滾、不顯示錯誤、直接顯示成功結果。

4. **逾時分支不能說「失敗」** —— 委託狀態未知，可能已成交。措辭必須是「請至明細確認」。

5. **送出中要防重複點擊** —— 按鈕停用 ＋ 全頁遮罩。冪等鍵是最後防線，不是唯一防線。

6. **成功用靛藍不用綠** —— 綠色在台股語意是「跌」。

7. **買賣方向要有文字** —— 不能只靠顏色，後果相反的操作必須有文字標示。

### 與設計的已知差異

- 無 Figma 設計稿，以 `04-design-system.md` 的 token 為準
- MVP 只做**限價單**，市價單需要模擬撮合深度，成本高且非本專案重點
- MVP 只做**全部成交或全部拒絕**，不做部分成交（但 `executions` 表結構已預留）
