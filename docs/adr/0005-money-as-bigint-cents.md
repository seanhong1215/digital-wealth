# ADR 0005 — 金額一律以整數「分」儲存，並用 branded type 標記

**狀態**：已採納｜**日期**：2026-08-13

## 背景

金融系統最基本也最致命的錯誤是浮點誤差。JavaScript 的 `0.1 + 0.2 !== 0.3`，在金額運算中會累積成對不上的帳。

同時，`number` 型別無法區分「元」與「分」，開發者很容易在某處忘記轉換。

## 決策

1. **資料庫金額欄位一律 `BIGINT`，單位為「分」**（1 元 = 100 分）
2. **API 回傳的金額也是分**，欄位名一律以 `Cents` 結尾
3. **所有金額運算集中於 `shared/money.ts`**，禁止在元件或 Service 中直接做金額算術
4. **型別用 branded type 標記**：

```ts
/** 金額的最小單位（分）。1 元 = 100 分。
 *  用 branded type 讓 TypeScript 阻止「把元當成分」的錯誤。 */
type Cents = number & { readonly __brand: 'Cents' };
```

5. **後端永遠不回傳格式化字串** —— 千分位、幣別符號都是前端的事

## 替代方案

| 方案 | 捨棄理由 |
|---|---|
| `DOUBLE PRECISION` / JS `number`（元） | **浮點誤差**，金融系統不可接受 |
| `NUMERIC(20,4)` | 精確但 JS 無原生對應型別，取出來是字串，每次都要轉換；運算較慢 |
| Decimal 函式庫（decimal.js） | 需額外依賴，且本專案不處理利率複利，整數已足夠 |
| 不用 branded type，直接 `number` | 編譯期無法阻止單位混用，只能靠命名約定與 review |

## 邊界

`BIGINT` 上限約 9.2 × 10¹⁸ 分。但 **JavaScript 的 `Number.MAX_SAFE_INTEGER` 是 9,007,199,254,740,991**（約 90 兆元），這才是實際上限。

本專案資料量級（帳戶餘額百萬級）完全安全。`shared/money.ts` 應包含執行期檢查並在超界時拋錯。

## 關於股數

**股數用 `BIGINT`，不用 `NUMERIC`。**

台股零股交易的最小單位是 **1 股（整數）**，不存在 0.5 股。需要小數的是**美股碎股**（fractional shares）。若未來支援美股情境，需改型別並在 `money.ts` 加小數運算。

## 後果

**正面**：精度絕對正確；branded type 在編譯期擋下單位混用；與 PostgreSQL `BIGINT` 直接對應。

**負面**：邊界需做單位轉換（API 輸入輸出、顯示層）；開發者需習慣「所有數字都是分」。
