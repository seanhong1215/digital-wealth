# ADR 0009 — 不做深色模式，但 token 分層預留

**狀態**：已採納｜**日期**：2026-08-13

## 背景

深色模式是現代 App 的常見期待，但實作成本不低：每個顏色都要有對應的深色值、每個元件都要在兩種模式下測試、圖表與圖片也要處理。

本專案的判準是 README §1：**這件事做完，能不能撐起一段有內容的技術討論？**

深色模式的答案是「不能」—— 它是工作量，不是技術難度。同樣的時間投入在交易一致性或 WebSocket 重連上，訊號強得多。

## 決策

**不實作深色模式。**

但 **Design Token 採用原始層／語意層兩層架構**，讓深色模式成為「架構上的延後」而非「做不到」。

```
原始層（Primitive）          語意層（Semantic）
--navy-900: #16243A    →    --color-text-primary
--navy-50:  #F5F7FA    →    --color-bg-page
```

支援深色模式時，**只需重新定義語意層的對應值，原始層完全不用動，元件程式碼一行都不用改**。

## 替代方案

| 方案 | 捨棄理由 |
|---|---|
| 完整實作深色模式 | 是工作量不是技術難度，訊號弱；且金融介面的漲跌色在深色底下需重新校正對比度，成本更高 |
| 單層 token，未來再重構 | 屆時要改遍所有元件，等於重做設計系統 |
| 只做 `prefers-color-scheme` 自動切換 | 仍需完整的深色色值與測試，成本相同 |

## 額外考量

金融介面的深色模式有特殊難點：**漲跌色在深色背景下的對比度需要重新校正**。`#DC2626`（紅）在白底對比 4.53:1 合格，但在深色底上會過暗，需改用較亮的紅（如 `#EF4444`）。

「知道要做什麼但刻意延後」與「沒想過」是兩件事，差別在 token 有沒有分層。

## 後果

**正面**

- 省下的時間投入更高價值的模組
- 兩層 token 架構同時解決了另一個問題：**市場情境切換**（台股紅漲 vs 美股綠漲），只需改語意層對應
- 「不做」是有理由的取捨，可寫進 README 作為判斷力展示

**負面**

- 需維護兩層 token，開發者需遵守「元件禁止直接使用原始層」的規範
- README 需明確說明這是刻意取捨，否則會被當成疏漏
