# ADR 0008 — 下單步驟走路由，表單資料不持久化

**狀態**：已採納｜**日期**：2026-08-13

## 背景

多步驟下單流程有兩種常見做法：全部在單一路由用內部 state 管理步驟，或每一步是獨立路由。

同時，表單資料是否要在重整後還原，是個看似「體驗優化」實則有安全意涵的決定。

本專案的交易明細頁**會**把篩選條件同步到 URL，下單表單是否比照辦理，需要明確的判準。

## 決策

| 項目 | 決定 |
|---|---|
| **步驟（step）** | **走路由** —— `/trade/:symbol/confirm` 等 |
| **表單資料** | **只存記憶體，重整回到步驟 1** |
| **`idempotencyKey`** | **進入確認頁時產生**（非按下送出時），存記憶體 |
| **結果頁** | 獨立路由，帶 `orderId` query |

## 理由

### 步驟走路由

瀏覽器上一頁能回到前一步，符合直覺；每一步可被書籤與分享；結果頁（尤其「下單被拒」）能用連結直接分享。

### 表單資料不持久化 ★

**金融場域的正確答案：下單草稿本來就不該被還原。**

使用者重整後看到一張已填好「買進 500 股」的確認頁，卻不記得是自己剛填的還是上次殘留 —— 這是真實系統會出事的地方。

**與明細篩選的對照：**

| | 明細篩選 | 下單表單 |
|---|---|---|
| 分享價值 | 高 | 無 |
| 意圖新鮮度 | 不重要 | **關鍵** |
| 誤操作後果 | 看到不對的列表 | **送出不想要的委託** |

### `idempotencyKey` 在進入確認頁時產生

若在按下送出時才產生，使用者連點兩次會產生**兩把不同的 key**，冪等完全失效。

在進入確認頁時產生一次並存在該步驟狀態裡，連點多少次帶的都是同一把。

```tsx
// lazy initializer 確保只執行一次
const [idempotencyKey] = useState(() => crypto.randomUUID());
```

## 替代方案

| 方案 | 捨棄理由 |
|---|---|
| 步驟用內部 state | 上一頁會直接離開流程；無法分享特定步驟 |
| 表單資料存 sessionStorage | 舊的下單意圖被還原是危險的 |
| 表單資料同步到 URL | 委託內容出現在網址列與瀏覽紀錄，且可被誤分享 |
| 送出時才產生冪等鍵 | 連點會產生不同 key，冪等失效 |

## 後果

**正面**：安全性正確；「為什麼明細同步 URL 但下單不要」的答案是「可分享性 vs 意圖新鮮度」的取捨。

**負面**：使用者誤觸重整需重填（可接受 —— 這是刻意的摩擦）；需在 README 說明這是設計而非缺陷。
