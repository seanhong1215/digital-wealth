# ADR 0004 — 後端只做本機 Docker Compose，前端另外靜態託管

**狀態**：已採納（2026-08-27 修訂，見文末）｜**日期**：2026-08-13

## 背景

原規劃靜態部署至 Vercel／GitHub Pages，理由是「無伺服器即無到期問題」。

改用真實後端後（[ADR 0001](0001-real-backend-over-msw.md)），需要常駐機器 + PostgreSQL + Redis，且 WebSocket 的長連線排除了所有 serverless 方案。

常見免費方案的實際下場：

| 平台 | 問題 |
|---|---|
| Render free | 15 分鐘無流量休眠，冷啟動數十秒；**免費 PostgreSQL 30 天到期**，再 14 天寬限後刪庫；背景常駐程序（`market-feed`）不在免費層 |
| Supabase free | 7 天無活動暫停專案 |
| Railway | 已無常駐免費層 |

這類示範專案最常見的死法就是「半年後打開，畫面全白」。而 30 天比半年還糟。

## 決策

**後端不做雲端部署，只提供本機 Docker Compose。**

`docker compose up` 一行啟動全套，自動執行 migration 與 seed。

## 替代方案

| 方案 | 捨棄理由 |
|---|---|
| Fly.io + Neon + Upstash（約 $5/月） | 需持續付費，且成本會隨時間累積 |
| 免費層 + 接受冷啟動 | 免費 PostgreSQL 會刪庫，30 天後 demo 直接死亡 |

## 後果

**正面**

- **完全消除到期風險** —— 沒有伺服器就沒有休眠、沒有帳單、沒有刪庫
- 零成本
- `docker compose up` 一行啟動本身是加分項，證明環境可重現

**負面（必須主動緩解）**

沒有線上連結，發現成本提高。緩解措施：

1. **README 首屏放 60 秒 GIF／影片** —— 從「選配」升為**必要交付**。不 clone repo 也能看到東西在動
2. **一行啟動** —— 不需任何手動步驟，README 標明啟動耗時與資源需求
3. **關鍵畫面截圖進 repo** —— 總覽、下單確認、下單被拒、報價中斷四張，放 `docs/screenshots/`
4. **前端另外靜態託管**（見下方修訂）

## 2026-08-27 修訂：前端拆出來部署

原決策說「不做雲端部署」，涵蓋了整個系統。實際落地時發現這個範圍畫得太寬 ——
**「不能部署」的其實只有後端**，前端沒有這個限制。

於是改成兩種展示分開：

| | 內容 | 託管 |
|---|---|---|
| **GitHub Pages** | 前端 UI，資料由瀏覽器裡的 MSW 提供 | 靜態，沒有伺服器就沒有到期問題 |
| **本機 Docker Compose** | 完整全端：真的行鎖、真的 pub/sub、真的 WebSocket | 使用者自己的機器 |

這讓上面第 1–3 點的緩解措施從「補償方案」變成「輔助說明」——
線上有一個真的能點的網站，截圖與影片只是讓人先知道會看到什麼。

**為什麼靜態版仍然有價值**：前端能原封不動地跑在假後端上，本身就證明了分層是乾淨的
（元件不直接 `fetch`，一律經由 feature 的 `api` 層）。而假資料是用
`shared/simulation` 產生的 —— 跟真實後端 seed 同一份規則、同一顆種子，數字完全一致。

**靜態版演不出來的**：並行競態。瀏覽器的 JavaScript 是單執行緒，
不可能有兩個請求同時讀到舊餘額 —— 而 `SELECT … FOR UPDATE` 正是本專案最核心的部分。
README 有明確標示這條界線，避免讓人以為線上版就是全部。

## 何時該推翻

若後端需要長期可公開存取（例如要接第三方 webhook、或要讓多人同時操作同一份資料），
應改為付費常駐部署（Fly.io + Neon + Upstash，約 $5/月）。
在那之前，付費換來的只是「省下 `docker compose up` 這一步」。
