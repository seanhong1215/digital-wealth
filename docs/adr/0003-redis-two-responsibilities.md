# ADR 0003 — Redis 只承擔兩個明確職責

**狀態**：已採納｜**日期**：2026-08-13

## 背景

技術棧規劃納入 Redis。但本專案資料量極小（持倉 8–15 檔、明細 3,000 筆），單純用來「快取」的話，PostgreSQL 自己就夠快 —— 這時 Redis 會變成**履歷驅動開發**（resume-driven development）。

面試官問「為什麼需要 Redis」，答不出來比不用還扣分。

## 決策

**保留 Redis，但只賦予兩個在金融場域站得住腳的職責**，並在 README 明寫。

| 職責 | 做法 | 為什麼是真需求 |
|---|---|---|
| **報價 pub/sub 扇出** | `market-feed` publish → `api` 訂閱 → 廣播給各 WebSocket 連線 | 真實交易系統的標準做法；讓多分頁／多裝置看到同一份報價 |
| **下單冪等鍵** | `SET idem:{key} NX EX 300` | 使用者連點兩次「確認下單」必須擋掉，券商系統一定要處理 |

**連帶決策**：`market-feed` 拆為獨立服務。若把它併進 `api`，Redis pub/sub 就失去存在理由。

## 替代方案

| 方案 | 捨棄理由 |
|---|---|
| 不用 Redis，冪等鍵只靠 DB UNIQUE | 可行但每次都要打資料庫；且失去展示 pub/sub 架構的機會 |
| 用 Redis 做通用快取 | 資料量太小，答不出「為什麼需要」 |
| 用 PostgreSQL `LISTEN/NOTIFY` 取代 pub/sub | 可行，但訊息無持久化保證、連線數受限，且業界即時場景仍以 Redis 為主流 |

## 後果

**正面**

- Redis 的存在有明確理由，是可談的技術點而非扣分項
- 冪等採**雙層防護**：Redis 是快速路徑（擋掉 99% 重複請求），DB UNIQUE 是最終保證（Redis 重啟不影響正確性）

**負面**

- 多一個服務要維護，Docker Compose 從 3 個容器變 5 個
- 需處理 Redis 斷線時的降級（報價停止推送，但下單仍須可用）
